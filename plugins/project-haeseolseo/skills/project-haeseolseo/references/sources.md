# 칸의 출처 찾기와 조사 분담 — GitHub 기준

**기준은 GitHub 저장소다.** 포트폴리오 사이트 · 발표자료 · 이력서는 저장소를 설명하려고 나중에 만든
글이라 틀릴 수 있다. 칸 · 순서 · 사실은 저장소에서 뽑고, 포트폴리오는 마지막에 대조만 한다.

## 사용자 환경 (처음에 물어서 메모리에 저장)
- 프로젝트 저장소들이 모여 있는 폴더
- GitHub 계정(`<owner>`), 사용자 자신의 git 작성자 이름과 커밋 메시지 서명 습관(예: 메시지 끝의 이름 표시)
- 포트폴리오 사이트 저장소가 있으면 그 위치와, 프로젝트별 화면 코드가 있는 폴더

## 1. 원격 기준 맞추기
```bash
git fetch origin
git log --oneline main..origin/main          # 로컬이 뒤처졌는지
git show origin/main:README.md               # README 는 원격 것을 읽는다
gh repo view <owner>/<repo> --json description,homepageUrl,defaultBranchRef
gh pr list -R <owner>/<repo> --state all --limit 50 --json number,title,author,mergedAt
```
코드가 같고 README 만 원격에 앞서 있으면, 코드 줄번호는 로컬로, 서술은 원격 README 로.

## 2. README 에서 뼈대 뽑기
README 는 대개 이런 절을 가진다. 있으면 그대로 칸이 된다.
| README 절 | 칸 |
|---|---|
| 머리 표(기간 · 인원 · 배포 · 내 몫) | 01 프로젝트와 팀 |
| 「5분만 있다면」 같은 핵심 코드 링크 | 코드 한 곳당 한 칸 |
| 「결정과 근거」 | 결정 한 개당 한 칸(또는 관련 코드 칸에 합침) |
| 「잰 것」 | 잰 것 칸 — 어떻게 쟀는지 · 말할 수 없는 것 표 |
| 「알고 있는 빚」 | 빚 · 회고 칸 + 해당 칸의 정직 표시 |
README 에 없지만 면접에서 반드시 나오는 것(인증, 데이터 모델, 배포, 트러블슈팅 커밋)은 칸을 추가한다.

## 3. 조사 분담 (서브에이전트 병렬)
각 프롬프트에 「읽기 전용, file:line + 원문 스니펫 ≤10줄, 불확실은 불확실로, 한국어 보고, 비밀값은 존재만」.
1. **백엔드 인증 · 권한 · 도메인**: 빌드 · 설정 · 환경변수 · 배포 파일, 보안 설정 전체, 로그인 흐름, 토큰 발급 · 검증,
   요청자 식별을 토큰에서 하는지 경로 값을 믿는지, 엔드포인트 목록, 테스트, 비밀값 이력
2. **핵심 기능 경로**: README 가 가리키는 흐름 끝까지(외부 API · 타임아웃 · 폴백 · 캐시 · 실패 처리)
3. **앱 · 배포 · 이력**: 화면 구조, 토큰 저장, API 주소 결정, 배포 워크플로와 연속 수정 커밋 diff,
   작성자별 기여(`git log --author`, `git blame` 합계), 월별 커밋, 코드 규모

## 4. 작성자 귀속 (README 문장을 믿지 않는다)
```bash
git blame -L <start>,<end> <file> | awk '{print $1,$2}' | sort | uniq -c   # 구간별 작성자
git log --reverse --format='%h %an %ad %s' --date=short -S'<식별자>' -- <path>   # 처음 만든 커밋
git show <hash>^:<file> | grep -n '<식별자>' -A5                            # 확장 전 모습
```
칸마다 「처음 만든 사람 / 넓힌 사람 / 지금 줄의 대부분」을 적는다. README 가 「내 결정」이라 쓴 것이
팀원이 먼저 만든 것을 넓힌 경우가 있다 — 해설서 답에서 반드시 구분한다.

## 5. 트러블슈팅은 커밋에서
- 짧은 시간에 몰린 연속 커밋(예: 30분에 4개), fix/수정/버그 메시지, 같은 날 연달아 바뀐 파일을 찾는다.
- 메시지가 「1」이어도 diff 는 거짓말하지 않는다. `git show <hash>` 로 무엇이 바뀌었는지 확인.
- 커밋 시각 순서로 인과를 세우되, 증상 기록이 없으면 「diff 로 재구성」이라고 명시하고
  「당시 실제로 본 증상」은 면접 전 확인으로 내린다.
- 설명 전에 연산자 · 기본값 같은 세부를 코드로 확인한다(예: `??` 는 빈 문자열을 기본값으로 넘기지 않는다).

## 6. 포트폴리오 · 이력서 대조 (마지막)
```bash
P="<포트폴리오 저장소>/<프로젝트별 화면 폴더>"
ls "$P/<slug>"; grep -rn '<클래스 · 엔드포인트 · 숫자>' "$P/<slug>"
```
- 포트폴리오 저장소에 프로젝트 데이터 파일(프로젝트 목록 · 이력서 데이터 · 감사 메모 등)이 있으면 그것도 본다.
- 저장소에 없는 클래스 · 엔드포인트 · 수치, 틀린 역할 귀속, 틀린 스택 이름을 목록으로 만들어 사용자에게 보고한다.

## 7. 포트폴리오 고치기 (사용자가 요청할 때)
- 이력서처럼 사용자가 작업 중인 파일(`git status` 로 확인)은 건드리지 말고 보고만 한다.
- 파일을 지우거나 이름을 바꾸지 않는다(삭제는 사용자 확인 필요). 같은 파일 · 같은 export 이름으로 내용을 바꾼다.
- 재현 데모는 남겨도 되지만 데이터는 저장소 원문(문항 · 사전 · 실제 응답)으로 채우고, 가정값은 화면에 가정이라고 쓴다.
- 코드 패널은 실제 파일의 실제 줄만. 파일명 옆에 줄 번호나 커밋 해시.
- 타입 검사 · 포매터 · 개발 서버로 렌더링 확인. 옛 주장 문구가 페이지 텍스트에 남았는지 스크립트로 검색한다.
- 커밋 · 푸시는 사용자가 요청할 때만.
