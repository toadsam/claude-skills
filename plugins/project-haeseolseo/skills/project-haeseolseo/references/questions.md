# 예상 질문 쓰는 법

## 세 단계
| 단계 | 클래스 | 무엇을 보나 | 칸마다 |
|---|---|---|---|
| 기본 | `t t1` | 뭘 만들었고 왜 그 기술인가. 개념 정의 | 1~2 |
| 꼬리 | `t t2` | 답에서 한 발 더: 다른 방법은? 규모가 커지면? 그 경우엔? | 1~3 |
| 압박 | `t t3` | 약점·모순·「그거 클라이언트를 믿는 거잖아요」 | 1~2 |

질문은 실제 면접관 말투로. 「~는 왜 그런가요?」「~면 어떻게 되나요?」「~아닌가요?」

## 질문을 찾는 곳
1. 칸이 주장하는 문장 하나하나 → 「왜?」「다른 방법은?」
2. 코드에서 발견한 **빈 곳** → 압박 질문 (속도 제한 없음, 타임아웃 없음, 클라이언트가 보낸
   userId 를 믿음, 테스트 없음, 비밀값이 이력에 있음)
3. 그 기술의 **단골 꼬리**: JWT → 세션과 차이·저장 위치·XSS/CSRF·키 유출.
   CORS → 프리플라이트·credentials·`*`. JPA → N+1·트랜잭션. 외부 API → 타임아웃·비용·장애 격리·
   프롬프트 인젝션. 캐시 → 무효화. 실시간 → 스케일아웃. 배포 → CI/CD·롤백·모니터링.
4. 팀 프로젝트 → 「그건 누가 했나요」「본인 기여는 정확히 뭔가요」「협업에서 갈등은」
5. 지원 도메인 → 금융이면 감사 추적·탐지·개인정보.

## 답 `.ans`
- 1인칭, 3~5문장, 소리 내 30초 안에.
- 구조: **결론 → 이유 → (있으면) 우리 코드의 사실 → 한계와 다음**.
- 확인한 사실만 단정한다. 확인 못 한 것은
  「정석은 ~이고, 제 구현이 그렇게 되어 있는지는 확인해서 답하겠습니다」 + 확인 항목 추가.
- 약점 질문엔 방어하지 않는다. 「맞습니다. ~라서 그렇게 했고, 지금이라면 ~」.
- 「모른다」를 숨기려고 교과서 설명을 길게 늘이지 않는다.

## 팁 `.tip`
넣을 때: 다음에 반드시 올 질문이 있을 때, 확인할 파일이 있을 때, 답의 톤 조언.
```html
<div class="tip"><b>팁</b> 「그래서 지금은 재사용 공격에 열려 있다는 거죠?」가 다음 질문입니다. 「네, …」로 인정하고 답하세요.</div>
```

## 예시 (토큰 재발급 칸, 압박)
> **Q.** 클라이언트에서 단일화하는 건 클라이언트를 믿는 거잖아요. 서버에서 풀어야 하는 것 아닌가요?
>
> **A.** 맞습니다. 클라이언트 단일화는 UX 문제(정상 사용자가 튕김)를 푼 것이지 보안을 더한 게
> 아닙니다. 프론트가 하나라 당장은 충분했지만, 클라이언트가 여럿이 되거나 로테이션을 다시
> 넣으려면 서버가 사용자별로 재발급을 직렬화해야 합니다. 거기에 family 로 재사용 감지를
> 붙이는 게 제가 생각하는 완성형입니다.

좋은 이유: 인정 → 무엇을 풀었고 무엇은 안 풀었는지 구분 → 당시 판단 근거 → 완성형 제시.
