# 칸 하나를 쓰는 법

칸(`section.lv`)은 아래 블록을 이 순서로 쓴다. 필수는 ★. 나머지는 칸에 맞을 때만.
예시는 「로그인 토큰 재발급」 같은 흔한 칸을 가정한 것이다.

## ★ 머리 `.lv-head`
`번호 · 제목 · (팀이면 by 배지) · 태그`. 태그는 출처 칸 이름이나 부제.
가장 중요한 칸은 태그에 「가장 중요한 칸」이라고 적는다.
```html
<div class="lv-head"><span class="n">04</span><h2>토큰 · 로테이션</h2><span class="tag">트러블슈팅 01 · 가장 중요한 칸</span></div>
```

## ★ 한 줄로 `.oneline`
기능 설명이 아니라 **문제와 선택**을 한 문장에.
- 나쁨: 「JWT 기반 인증을 구현했다.」
- 좋음: 「교과서대로 보안을 넣었더니 사용자가 튕겼고, 왜 그런지 이해한 뒤 다른 방법으로 막았다.」

## ★ 본문 `.body`
2~5 문단. 흐름은 **무엇이 문제였나 → 바닥 원리 → 우리 선택**.
- 바닥 원리 문단은 `<strong>바닥 원리.</strong>` 로 시작한다. 긴 칸은 `① ② ③` 단계로 쪼갠다
  (예: 로그인 상태 기억 → 출입증 둘 → 보관 위치 → 훔쳤다면 → 실제로 켜 보니).
- 면접에서 한 문장으로 이해를 증명하는 문장을 넣는다.
  예: 「CORS 는 브라우저의 규칙이지 서버의 규칙이 아닙니다.」
- `.analogy` 비유 하나. 「로테이션은 출입증을 갱신하면 옛 출입증은 그 자리에서 파쇄」.
- 새 용어는 `<em>` 로 표시하고 용어 사전에 올린다.

## 재현 실험 `.lab`
원리를 **눌러서 보는** 곳. 칸의 핵심 주장 하나만 증명한다. 패턴은 `labs.md`.
설명용 숫자는 `.note` 에 「숫자는 설명용 가정입니다」.

## 우리 코드 `.code`
실제 파일에서 5~12줄. `.fn` 에 경로와 「우리 코드」. 핵심 줄은 `.hi`, 한국어 주석 `.cm`.
포트폴리오가 보여 준 코드와 실제 코드가 다르면 **실제 코드**를 싣고 차이를 정직 표시에 적는다.
생략은 `...` 로 표시하되 로직을 바꾸지 않는다.

## 구조 그림 `figure > svg`
갈래가 합류하거나 요청이 여러 층을 지나는 칸에만. 인라인 SVG, `currentColor` 로 테마 대응,
`role="img"` + `aria-label`, `figcaption` 한 줄.

## 포트폴리오 대조 `.claim` (기본은 쓰지 않음)
해설서는 저장소 기준이라 본문에 포트폴리오 대조표를 넣지 않는다. 사용자가 포트폴리오를 고치지 않기로 했을 때만,
어긋난 칸에 `.claim` 표(`포트폴리오 | 저장소 | 판정` + `.vd.same/.diff/.none` + `.say`)를 붙인다.

## 정직 표시 `.honest`
- `<b>정직 표시</b>` 측정하지 않은 것, 설명용 값, 포트폴리오 주장과 코드의 차이
- `<b>아직 안 한 것</b>` 남은 과제와 근거(커밋 해시, 문서 위치)

## 방법 비교표 `.tbl` (「다시 넣는다면」)
트러블슈팅 칸이나 설계 선택 칸에. 열은 `방법 | 어떻게 | 막는 것 | 못 막는 것·비용`.
지금 방식도 한 줄로 넣고, 표 아래 `.note` 에 「지금 구현은 X 이고, Y 가 되면 Z 가 맞다」.

## ★ 예상 질문 `.qa-list` — `questions.md`

## ★ 면접 전 확인 `.check`
답을 하려면 저장소를 직접 봐야 하는 것. 체크하면 저장되고 목차에 ✓ 가 붙는다.
- 구체적으로: 파일 경로, 설정 키, 확인할 값. 「보안 확인」 같은 막연한 항목 금지.
- 조사에서 **확인하지 못한 것**과 **포트폴리오 주장과 어긋난 것**은 반드시 여기에.
- 이미 코드로 확인한 사실은 확인 항목이 아니라 본문·답에 쓴다.

## 문서 전체의 고정 칸

### 답하는 법 `#howto` (맨 앞)
`.strategy` 박스 4~6개: 답의 뼈대 4단 · 모를 때 하는 말 · 숫자를 말할 때(README·운영에서 실제로
잰 것/안 한 것) · 가장 강한 카드(칸 번호). 팀 프로젝트면 「내 몫과 팀 몫」(blame·커밋 기준)과
「가장 위험한 질문」(README 만 읽으면 오해할 귀속·빚) 박스 추가.

### 결과 · 회고 (마지막 번호 칸)
- 「진짜와 재현 구분」 표: 실제 코드 / 실제 화면 / 설명용 예시 / 측정 안 해서 안 적음
- 배운 것 표(단계·버전별이면 두 열)
- 팀이면 사람별 담당 표(근거 커밋)
- 종합 질문: 30초 요약 · 가장 어려웠던 점 · 다시 한다면 · 지원 도메인(은행 등)이라면 부족한 것 ·
  「본인이 이해한 부분과 도움받은 부분 구분」(압박)

### 용어 사전 `#gloss`
문서에 나온 순서대로 `dt/dd`. 한 줄 정의, 가능하면 비유. 짝 개념은 한 줄에 「A / B」.

### 모의 면접 카드 `#drill`
템플릿 그대로(목차 자리만). 실제 화면은 껍데기의 「말하기 연습」이 문서의 모든 `details.qa` 로 만든다. 손대지 않는다.

## 문체
- 본문은 「~입니다」 설명체, 답은 「~했습니다」 1인칭.
- `word-break:keep-all` 이 걸려 있으니 영문·코드 앞뒤에 공백을 둔다 (「HTTP 는」).
- 한 문단 한 생각. 과장 금지(「완벽하게」「획기적」). 약점은 먼저 말한다.
