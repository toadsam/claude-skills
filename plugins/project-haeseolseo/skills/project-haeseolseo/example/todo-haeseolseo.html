답하는 법

칸에 들어가기 전에

포트폴리오 질문은 거의 같은 순서로 옵니다. 「뭘 만들었나」 → 「왜 그렇게 했나」 → 「다른 방법은」 → 「그때 뭐가 문제였나」 → 「지금 다시 하면」. 이 문서의 예상 질문도 기본 → 꼬리 → 압박 순서입니다.

답의 뼈대 4단문제 → 원인 → 해결 → 배운 것. 02칸(검증을 어디서 하나)이 이 틀에 가장 잘 맞습니다. 한 문장씩 네 문장이면 충분합니다.
모를 때 하는 말「그 부분은 이 프로젝트에서 다루지 않았습니다. 정석은 ~이고, 제 코드가 그렇게 되어 있는지는 확인해서 말씀드리겠습니다.」 지어내면 꼬리 질문에서 무너집니다.
숫자를 말할 때이 예시는 아무것도 재지 않았습니다. 사용자 수 · 응답 시간 · 오류율이 없습니다. 「재지 않았다」를 먼저 말하고, 무엇을 어떻게 재겠다로 잇습니다.
가장 강한 카드 둘① 화면과 서버 양쪽에서 입력을 검사하는 이유를 코드로 보여 줄 수 있는 것(02). ② 데이터가 메모리에 있다는 한계를 먼저 말하고 다음 단계를 제시하는 것(03).
01

프로젝트 한눈에

내 담당README · web/ · server/
한 줄로할 일을 적고 목록으로 보는 가장 작은 앱을, 화면과 서버를 나눠서 만들었다.

저장소에는 프로그램이 둘 있습니다. web/ 은 React 화면이고, server/ 는 Express API 입니다. 화면은 GET /todos 로 목록을 받고 POST /todos 로 새 할 일을 보냅니다. 데이터는 진짜 DB 가 아니라 서버 메모리에 있습니다(03칸).

바닥 원리. 화면과 서버를 왜 나누나. 화면은 사용자의 브라우저에서 돌고, 사용자는 그 코드를 마음대로 고칠 수 있습니다. 그래서 「무엇을 저장해도 되는지」 같은 규칙은 사용자가 손댈 수 없는 서버가 지킵니다. 화면은 보여 주고 입력받는 일, 서버는 규칙과 저장을 맡습니다.

비유 화면은 식당 홀, 서버는 주방입니다. 손님은 홀에서 메뉴판을 마음대로 접을 수 있지만, 무엇을 요리할지는 주방이 정합니다.

02

할 일 추가 흐름

내 담당TodoList.tsx → api.ts → app.ts → todoService.ts · 가장 중요한 칸
한 줄로빈 제목은 화면에서 한 번 막고 서버에서 다시 막는다. 화면 검사는 편의이고, 서버 검사가 규칙이다.

사용자가 「추가」를 누르면 handleAdd 가 앞뒤 공백을 지우고, 비었으면 아무것도 보내지 않습니다. 비어 있지 않으면 addTodo 가 POST /todos 를 보내고, 서버는 title 이 문자열이고 비어 있지 않은지 다시 봅니다. 통과하면 createTodo 가 번호를 붙여 저장하고 201 과 새 할 일을 돌려줍니다. 화면은 그걸 목록 맨 앞에 붙입니다.

바닥 원리. 화면 검사는 왜 믿을 수 없나. 화면을 거치지 않고도 요청은 보낼 수 있습니다. curl -X POST /todos -d '{}' 한 줄이면 화면의 검사를 건너뜁니다. 그래서 화면 검사는 「쓸데없는 요청을 줄이는 친절」이고, 「잘못된 데이터를 막는 규칙」은 서버가 맡습니다.

비유 홀 직원이 「그 메뉴는 없어요」 하고 미리 말해 주는 건 친절이고, 주방이 없는 재료로는 요리하지 않는 건 규칙입니다. 직원을 건너뛰고 주방에 직접 소리쳐도 규칙은 그대로입니다.
재현「우유 사기」를 추가하면 · 단계를 하나씩 넘겨 보세요

요청과 응답은 코드를 따라 쓴 재현입니다. 실제 서버를 부르지 않습니다.

server/src/app.ts:13-19 · 우리 코드app.post("/todos", (req, res) => { const title = req.body?.title; if (typeof title !== "string" || title.length === 0) { // 화면을 건너뛴 요청도 여기서 막힌다 return res.status(400).json({ error: "title is required" }); } res.status(201).json(createTodo(title)); });
web/src/TodoList.tsx:13-23 · 우리 코드async function handleAdd() { const title = text.trim(); if (!title) return; // 화면 검사: 빈 요청을 아예 안 보낸다 try { const created = await addTodo(title); setTodos((prev) => [created, ...prev]); // 서버가 준 번호를 그대로 쓴다 setText(""); } catch (e) { setError("추가하지 못했어요"); } }
정직 표시 서버는 공백만 있는 제목(" ")을 막지 않습니다. 화면은 trim() 하지만 서버는 길이만 보기 때문에, 화면을 건너뛴 요청이면 공백 할 일이 저장됩니다. 200자 자르기는 서비스에 있고 오류 없이 조용히 잘립니다.

다시 한다면 · 검사를 두는 곳 비교

방법어떻게막는 것못 막는 것 · 비용
화면 + 서버 길이 검사 (지금)화면은 trim, 서버는 문자열 · 길이빈 제목, 잘못된 타입공백만 있는 제목, 200자 넘는 제목은 조용히 잘림
스키마 검사 라이브러리요청 본문을 스키마로 선언하고 서버 입구에서 검사타입 · 길이 · 공백을 한곳에서의존성 하나, 오류 메시지 형식 정하기
화면과 서버가 같은 스키마 공유스키마 파일을 두 쪽이 함께 import규칙이 어긋나는 것 자체저장소 구조가 복잡해짐

지금 다시 한다면 서버에서 title.trim() 을 먼저 하고, 200자를 넘으면 자르지 않고 400 을 돌려주겠습니다. 조용히 바꾸는 것보다 알려 주는 쪽이 낫습니다.

예상 질문

기본할 일을 추가하면 어떤 순서로 처리되나요?
화면이 공백을 지우고 비었는지 본 뒤 POST /todos 를 보냅니다. 서버는 제목이 문자열이고 비어 있지 않은지 다시 검사하고, 통과하면 번호를 붙여 저장한 뒤 201 과 새 할 일을 돌려줍니다. 화면은 서버가 준 객체를 목록 맨 앞에 붙입니다.
기본화면에서 이미 막는데 서버에서 또 검사하는 이유는요?
화면은 사용자가 고칠 수 있고, 요청은 화면 없이도 보낼 수 있기 때문입니다. 화면 검사는 쓸데없는 요청을 줄이는 편의이고, 잘못된 데이터를 막는 규칙은 서버가 지켜야 합니다.
꼬리새 할 일을 목록에 붙일 때 서버에서 목록을 다시 받지 않는 이유는요?
서버가 만든 객체(번호 포함)를 응답으로 주니까 그걸 맨 앞에 붙이면 서버 목록과 같은 순서가 됩니다. 요청 하나를 아낍니다. 대신 다른 사람이 동시에 추가한 항목은 새로고침 전까지 안 보입니다.
팁 「낙관적 업데이트」와 헷갈리지 마세요. 이 코드는 응답을 받은 뒤에 붙이니 낙관적 업데이트가 아닙니다.
꼬리200자를 넘는 제목은 어떻게 되나요?
서비스에서 200자로 잘려 저장되고, 사용자는 잘렸다는 걸 모릅니다. 조용히 바꾸기보다 400 으로 알려 주는 게 맞다고 생각하고, 고친다면 화면 입력창에도 같은 최대 길이를 걸겠습니다.
압박공백만 있는 제목은 서버를 통과하잖아요. 그럼 서버 검사도 불완전한 것 아닌가요?
맞습니다. 화면은 trim 하지만 서버는 길이만 봐서, 화면을 건너뛴 요청이면 공백 할 일이 저장됩니다. 서버에서 trim 한 뒤 길이를 보는 한 줄이면 고쳐지고, 같은 이유로 검사를 한곳에 모으는 스키마 검사를 넣고 싶습니다.

03

메모리 저장소

내 담당server/src/db.ts · 알고 있는 빚
한 줄로할 일은 서버 메모리의 배열에 있어서, 서버를 끄면 전부 사라지고 서버를 두 대로 늘리면 목록이 갈라진다.

db.ts 는 객체 하나입니다. todos 배열과 다음 번호 nextId. 진짜 DB 를 붙이기 전에 흐름부터 만들려고 이렇게 뒀고, 파일 주석에도 「서버를 끄면 사라진다」고 적었습니다.

바닥 원리. 상태가 어디 사는가. 프로그램이 기억하는 값(상태)은 메모리에 있고, 메모리는 프로그램이 끝나면 비워집니다. 끝나도 남아야 하는 값은 디스크(파일, DB)에 써야 합니다. 또 서버를 두 대 띄우면 메모리도 두 벌이라, 어느 서버에 요청이 갔느냐에 따라 다른 목록을 보게 됩니다.

재현할 일을 넣고 서버를 껐다 켜 보세요
서버 A 메모리
[]
nextId 1
서버 B 메모리
—
꺼져 있음
// 서버가 막 떴습니다. 목록은 비어 있습니다

서버 두 대는 「늘린다면」의 가정입니다. 이 예시는 한 대만 돕니다.

server/src/db.ts:1-7 · 우리 코드export type Todo = { id: number; title: string; done: boolean }; // 예시라서 진짜 DB 대신 메모리에 둔다. 서버를 끄면 사라진다. export const db = { nextId: 1, todos: [] as Todo[], };
아직 안 한 것 영구 저장, 완료 표시(done 은 있지만 바꾸는 API 가 없음), 삭제. 목록 정렬은 요청마다 배열 전체를 복사해 정렬합니다(todoService.ts:4).

예상 질문

기본데이터는 어디에 저장하나요?
서버 메모리의 배열입니다. 흐름을 먼저 만들려고 DB 없이 시작했고, 그래서 서버를 끄면 데이터가 사라집니다. 다음 단계는 파일 하나짜리 DB 인 SQLite 를 붙이는 것입니다.
꼬리번호(id)는 어떻게 붙이나요? 겹칠 수는 없나요?
nextId 를 하나씩 올립니다. Node 는 요청을 한 스레드에서 차례로 처리해서, 서버가 한 대면 겹치지 않습니다. 서버가 두 대면 둘 다 1 부터 세서 겹칩니다. 그래서 번호는 DB 가 붙이게 하는 게 맞습니다.
꼬리목록 정렬이 요청마다 일어나는데 괜찮나요?
할 일이 몇십 개면 문제없습니다. 몇만 개가 되면 요청마다 복사하고 정렬하는 비용이 커집니다. 번호가 커지는 순서로 쌓이니 뒤집기만 해도 되고, DB 를 붙이면 ORDER BY id DESC LIMIT 로 필요한 만큼만 가져오겠습니다.
압박데이터가 사라지는 앱을 포트폴리오에 넣는 게 맞나요?
기능으로는 부족합니다. 이 저장소에서 보여 드리고 싶은 건 화면과 서버의 역할 분리와 입력 검사 위치이고, 저장은 의도적으로 미뤘다는 걸 코드 주석과 README 에 적었습니다. 영구 저장을 붙이는 순서도 설명드릴 수 있습니다.

04

API 주소 · CORS

내 담당web/src/api.ts:3 · server/src/app.ts:6
한 줄로화면은 서버 주소를 빌드할 때 받는데, 빈 문자열은 기본값으로 넘어가지 않는다. 서버는 모든 출처를 허용해 두었다.

바닥 원리 ① 빌드 시점 값. import.meta.env.VITE_API_URL 은 실행할 때 읽는 게 아니라 빌드할 때 번들에 문자열로 박힙니다. 그리고 ?? 는 값이 null · undefined 일 때만 오른쪽을 씁니다. .env 에 VITE_API_URL= 처럼 빈 값이 들어가면 주소가 빈 문자열이 되고, 요청은 /todos 상대 경로로 화면이 떠 있는 서버에 갑니다.

② CORS. 화면(localhost:5173)과 서버(localhost:3000)는 포트가 달라 브라우저가 다른 출처로 봅니다. 서버의 cors() 는 옵션 없이 쓰여 모든 출처를 허용합니다. 개발에는 편하지만, 배포하면 아무 사이트가 이 API 를 불러 응답을 읽을 수 있습니다.

재현.env 값에 따라 요청이 어디로 가나

예상 질문

기본CORS 가 뭔가요? 왜 필요했나요?
다른 출처의 응답을 브라우저가 읽어도 되는지 서버가 허락하는 규칙입니다. 화면과 서버의 포트가 달라 브라우저가 다른 출처로 보고 막았고, 서버에 cors 미들웨어를 넣어 허락했습니다. 지금은 옵션 없이 모든 출처를 허용합니다.
꼬리?? 대신 || 를 쓰면 뭐가 달라지나요?
|| 는 빈 문자열 · 0 같은 거짓 값에도 오른쪽을 씁니다. 주소처럼 빈 문자열이 의미 없는 값이면 || 가 맞습니다. 지금 코드는 ?? 라서 빈 값이 들어오면 상대 경로로 요청이 갑니다.
압박모든 출처를 허용하면 위험하지 않나요?
배포하면 위험합니다. 지금은 쿠키나 인증이 없어서 다른 사이트가 할 수 있는 건 목록을 읽고 추가하는 것뿐이지만, 로그인을 붙이는 순간 문제가 됩니다. 배포할 때는 허용 출처를 화면 주소 하나로 좁히고, 그 값을 환경변수로 빼겠습니다.
압박CORS 를 열면 서버가 보호되나요?
아닙니다. CORS 는 브라우저가 지키는 규칙이라 curl 같은 도구에는 아무 의미가 없습니다. 서버 보호는 인증과 입력 검사가 하고, CORS 는 사용자의 브라우저가 다른 사이트에 우리 응답을 넘기지 않게 하는 장치입니다.

기본30초로 요약해 주세요.
할 일을 적고 보는 작은 앱을 React 화면과 Express 서버로 나눠 만들었습니다. 빈 제목은 화면에서 한 번, 서버에서 다시 막고, 서버 검사를 규칙으로 봤습니다. 데이터는 아직 메모리에 있어서 영구 저장이 다음 단계입니다.
기본가장 어려웠던 점은요?
검사를 어디에 둘지 정하는 것이었습니다. 화면에서 막으면 사용자 경험이 좋아지지만, 그것만으로는 규칙이 안 된다는 걸 curl 로 요청을 보내 보고 알았습니다. 그래서 같은 검사를 서버에도 넣었고, 그래도 공백 제목이 남는다는 걸 뒤에 발견했습니다.
꼬리다시 처음부터 한다면 무엇을 바꾸나요?
처음부터 SQLite 를 붙이고, 요청 본문을 스키마로 검사하고, POST /todos 테스트 두 개를 먼저 쓰겠습니다. 셋 다 작지만 지금 문서에 적은 약점을 거의 다 없앱니다.
압박본인이 이해하고 짠 부분과 도움을 받은 부분을 구분해 주세요.
구분 기준은 「무엇이 왜 그렇게 되어 있는지 설명할 수 있는가」라고 생각합니다. 검사 위치, 메모리 저장의 한계, ?? 와 빈 문자열 문제는 지금 코드를 열어 설명드릴 수 있습니다.
팁 이 문서를 끝까지 읽고 확인 항목을 채우면 위 문장이 사실이 됩니다.

용어 사전

문서에 나오는 순서대로
API
프로그램끼리 주고받는 약속. 여기서는 GET /todos, POST /todos.
Express
Node 에서 주소별로 요청을 받아 처리하는 작은 서버 라이브러리.
useState
React 화면이 기억하는 값. 바뀌면 화면을 다시 그린다.
fetch
브라우저에서 서버로 요청을 보내는 함수.
400 / 201
요청이 잘못됨 / 새로 만들었음.
trim
문자열 앞뒤 공백을 지우는 것.
낙관적 업데이트
서버 응답을 기다리지 않고 화면을 먼저 바꾸는 것. 이 앱은 하지 않는다.
스키마 검사
요청 모양(타입 · 길이)을 선언해 두고 입구에서 한 번에 검사하는 것.
메모리 / 디스크
프로그램이 끝나면 비는 곳 / 끝나도 남는 곳.
이벤트 루프
Node 가 요청을 한 스레드에서 차례로 처리하는 방식.
빌드 시점 값
빌드할 때 번들에 문자열로 박히는 설정. 바꾸려면 다시 빌드.
?? / ||
null · undefined 일 때만 기본값 / 빈 문자열 · 0 에도 기본값.
출처 (origin) / CORS
프로토콜 + 도메인 + 포트 / 다른 출처의 응답을 읽어도 되는지 서버가 허락하는 규칙.
