# 업데이트가 하는 일

## 왜 줄 번호가 아니라 지문인가

예전 방식은 해설이 "638번째 줄"에 묶여 있어서, 파일 위에 한 줄만 생겨도 아래 해설이 전부 한 칸씩 어긋났다.
지금은 build.js 가 덩어리마다 **지문(fp)** 을 붙인다: 그 덩어리 코드 줄들(줄 끝 공백 제외)의 FNV-1a 해시, `"b" + 8자리`.
줄 번호가 바뀌어도 내용이 같으면 지문이 같다.

- 페이지의 "읽음" 기록 = `구간 이름#지문`. 내용 같은 덩어리는 옮겨져도 읽음 유지, 바뀐 덩어리는 다시 안 읽음.
- 구간 이름(chunk key)은 `파일@처음 from`. 구간이 옮겨지면 update.js 가 annot 에 `key` 를 남겨 이름을 유지한다.
- 예전 페이지(번호 기록 `파일#3`)를 보던 사람은 새 페이지를 처음 열 때 자동으로 지문 기록으로 바뀐다.

## manifest.json (build.js 가 매번 씀)

`{ buildId, builtAt, commit, commitDate, repo, chunks: { 구간: { path, from, to, fps } }, files: { 경로: [가린 뒤의 줄들] } }`
업데이트의 기준. 지우지 않는다. (저장소 밖 작업 폴더에만 있고, 비밀 값은 이미 가려져 있다.)

## update.js 순서

1. 파일마다 manifest 의 옛 줄 ↔ 지금 줄을 맞춘다(같은 줄끼리 최장 공통 부분열, 앞뒤 같은 부분은 먼저 자름. 아주 큰 파일은 고유한 줄만).
2. 구간(from~to): 첫 · 끝 줄이 살아 있으면 그 새 위치, 바뀌었으면 가장 가까운 살아 있는 줄 기준으로 옮긴다. 구간 안에 끼어든 새 줄은 구간에 포함.
3. 덩어리: 앞 덩어리 끝 다음 줄부터 시작하도록 이어 붙인다(빈틈 없음 유지). 덩어리 사이에 끼어든 새 줄은 **뒤 덩어리**로 들어간다.
   - 새 줄도 지워진 줄도 없으면 → 그대로(줄 해설 번호만 이동)
   - 하나라도 있으면 → `review: { status, newLines, deletedLines, droppedNotes }`
   - 줄이 전부 지워진 덩어리 → 빠짐(worklist 의 "지워진 덩어리")
4. 따라가기 단계도 같은 방식으로 옮기고, 범위 안이 바뀌었으면 `review`.
5. git 이 있으면 `git diff --name-status <manifest 커밋>` + 아직 커밋 안 한 새 파일로 새 파일 · 지운 파일 · 이름 바꿈을 알려 준다.
6. 고치기 전 `backup/<시각>/` 에 config · 바뀐 annot · tours 를 복사한다.
7. `pending-update.json` 에 옛 판 번호 · 옛 지문 목록(경로별) · 줄 옮김표(`[옛 시작, 새 시작, 길이]` 묶음)를 남긴다 → 다음 build 가 페이지에 넣는다.

## 페이지에서

- `DATA.changes.blocks`: 옛 지문 목록에 없는 덩어리 = "바뀜"(그 경로가 전에 있었으면) / "새로". 읽기 홈 맨 위 목록, 덩어리 지도 초록 점.
- 별표 · 틀린 줄(`경로|줄`)은 보는 사람이 **바로 앞 판**에서 왔을 때 줄 옮김표로 새 줄로 옮긴다. 바뀐 줄의 별표는 빠지고 알림이 뜬다. 판을 건너뛰면 옮기지 못한다(그대로 둔다).

## 한계 · 판단이 필요한 곳

- 파일 이름이 바뀌면(이동 포함) 다른 파일로 본다 → worklist 의 "이름 바꿈"을 보고 config 의 경로와 annot 의 file 을 직접 바꾼 뒤 update 를 다시 돌린다.
- 함수가 파일 안에서 위치만 바뀌면(위아래 이동) 공통 부분열이 한쪽만 살린다 → 그 덩어리는 review 로 뜬다. 해설 내용은 그대로 써도 되는지 보고 review 만 지우면 된다.
- 바뀐 줄 비율이 30% 를 넘으면 덩어리 고치기보다 흐름을 처음부터 다시 만드는 게 깔끔할 수 있다 → 사용자에게 묻는다.
- 따라가기 이야기의 "줄거리"(어떤 순서로 무엇을 부르는지)가 바뀌었으면 단계 추가 · 삭제가 필요하다. update.js 는 줄만 옮기니, review 단계 주변의 흐름을 직접 확인한다.
- 사전 · 평가 · 지도는 자동으로 고치지 않는다. 관련 파일(설정 · .env 예시 · DB 저장 코드 · 배포 설정)이 바뀌었는지 worklist 의 파일 목록으로 보고 손본다.
